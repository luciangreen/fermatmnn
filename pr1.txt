MNN Prolog Program Requirements

Requirements for GitHub Copilot Agent

Project name: MNN
Expanded name: Manual Neuronet
Primary implementation language: SWI-Prolog
Primary interface: Interactive SWI-Prolog REPL
Primary purpose: Transparent symbolic reasoning, algorithm synthesis, dependency optimisation and research hypothesis generation

⸻

1. Project objective

Implement an initial Manual Neuronet system in SWI-Prolog.

The program must represent knowledge as explicit:

* domains;
* concepts;
* facts;
* claims;
* rules;
* questions;
* examples;
* constraints;
* dependencies;
* algorithms;
* proof obligations;
* research hypotheses.

The system must use these structures to:

1. answer questions from explicit rules;
2. generate small candidate algorithms from examples;
3. identify necessary and unnecessary computations;
4. convert selected nondeterministic patterns into deterministic structures;
5. represent alternatives using explicit choice packets;
6. construct and schedule dependency graphs;
7. generate complete reasoning and optimisation traces;
8. distinguish proven conclusions from candidates, conjectures and empirical patterns;
9. output generated SWI-Prolog code;
10. execute generated code when requested.

The first version must be transparent and deterministic wherever possible. It must not depend on neural-network libraries, large language models or opaque statistical weights.

⸻

2. Working definition

A Manual Neuronet is:

A transparent symbolic network of typed concepts, explicit correlations, logical conditions, dependencies, constraints and executable actions that derives conclusions or algorithms through inspectable rule activation rather than opaque learned weights.

The program must treat this as an engineering definition rather than a claim that the system reproduces biological neurons.

⸻

3. First-release scope

The first release must implement:

* SWI-Prolog only;
* an in-SWI-Prolog REPL;
* file-based domain loading;
* explicit rule representation;
* forward reasoning;
* limited backward reasoning;
* question hotlists;
* claim-status classification;
* positive dependencies;
* negative constraints;
* necessary-variable analysis;
* small decision-tree synthesis;
* simple recursive-list synthesis;
* memoisation suggestions;
* deterministic choice packets;
* explicit splice operations;
* static dependency-graph construction;
* sequential and controlled parallel scheduling;
* reasoning traces;
* optimisation traces;
* generated Prolog output;
* optional immediate execution;
* benchmark support;
* a small number-theory demonstration domain.

The first release must not attempt:

* unrestricted natural-language understanding;
* unrestricted theorem proving;
* arbitrary Prolog program optimisation;
* automatic formal proof completion;
* general-purpose chatbot behaviour;
* autonomous scientific publication;
* distributed computing across machines;
* GPU execution;
* quantum execution;
* unrestricted robot control;
* semantic equivalence proofs for arbitrary programs.

⸻

4. Primary operating modes

The program must support the following modes.

mode(explain).
mode(answer).
mode(synthesise).
mode(optimise).
mode(schedule).
mode(research).
mode(verify).
mode(benchmark).

4.1 Explain mode

Explain:

* why a conclusion follows;
* which rules were used;
* which facts were required;
* which alternatives were rejected;
* which assumptions remain;
* whether the conclusion is proven, empirical or conjectural.

4.2 Answer mode

Answer a structured question using loaded domain knowledge.

4.3 Synthesise mode

Construct a candidate algorithm from:

* input-output examples;
* permitted operations;
* forbidden operations;
* type constraints;
* termination limits.

4.4 Optimise mode

Analyse an existing supported Prolog predicate and propose or perform selected transformations.

4.5 Schedule mode

Construct an execution schedule from explicit tasks and dependencies.

4.6 Research mode

Generate:

* candidate correlations;
* candidate formulas;
* candidate invariants;
* perturbations;
* missing dependencies;
* proof obligations.

4.7 Verify mode

Test a claim, algorithm or transformation against:

* examples;
* counterexamples;
* property checks;
* reference implementations;
* bounded mathematical searches.

4.8 Benchmark mode

Compare original and transformed programs.

8. Domain representation

A domain must be represented explicitly.

Required core structure:

mnn_domain(
    DomainId,
    Metadata
).

Example:

mnn_domain(
    primality,
    [
        title("Primality and Fermat Tests"),
        version(1),
        status(experimental),
        parent(number_theory)
    ]
).

8.1 Domain contents

A domain file may contain:

mnn_concept/3.
mnn_fact/3.
mnn_claim/5.
mnn_rule/6.
mnn_question/4.
mnn_hotlist/2.
mnn_example/4.
mnn_constraint/4.
mnn_operation/4.
mnn_dependency/4.

8.2 Domain inheritance

Support parent domains.

mnn_domain_child(Child, Parent).

Inherited content must be inspectable.

The system must report whether a fact or rule was:

* defined locally;
* inherited;
* imported through a domain bridge.

8.3 Domain bridges

Support:

mnn_domain_bridge(
    FromDomain,
    ToDomain,
    AllowedItems
).

Example:

mnn_domain_bridge(
    primality,
    modular_arithmetic,
    [
        predicate(gcd/3),
        predicate(pow_mod/4),
        concept(congruence)
    ]
).

The reasoner must not import unrelated rules across domains without an explicit bridge or parent relationship.

* merge compatible metadata;
* remain as separate sourced assertions;
* generate a conflict diagnostic when incompatible.

11. Claim representation

Required form:

mnn_claim(
    ClaimId,
    Proposition,
    Status,
    Scope,
    Metadata
).

Supported statuses:

status(proven).
status(formally_verified).
status(logically_derived).
status(computationally_verified(Bounds)).
status(empirically_supported(Data)).
status(candidate).
status(conjecture).
status(refuted).
status(unknown).

The program must never silently promote a weaker status to a stronger one.

A conclusion derived exclusively from empirical claims cannot automatically become proven.

12. Rule representation

Required form:

mnn_rule(
    RuleId,
    Conditions,
    Conclusion,
    Action,
    Status,
    Metadata
).

Example:

mnn_rule(
    fermat_failure_composite,
    [
        integer(N),
        greater_than(N, 1),
        fermat_test(N, Base, failed)
    ],
    composite(N),
    cancel(unnecessary_primality_tests(N)),
    proven,
    [
        domain(primality),
        source(fermat_little_theorem)
    ]
).

12.1 Condition forms

The first release must support conditions including:

positive(Goal).
negative(Goal).
known(Variable).
unknown(Variable).
equals(A, B).
not_equals(A, B).
greater_than(A, B).
less_than(A, B).
member_of(Value, Set).
all(Conditions).
any(Conditions).
not(Condition).

Ordinary callable Prolog goals may be supported only when explicitly permitted by the domain.

12.2 Rule actions

Supported action forms:

conclude(Proposition).
ask(Question).
run(Goal).
cancel(Target).
schedule(Task).
generate_code(Specification).
add_constraint(Constraint).
create_proof_obligation(Goal).
record_hypothesis(Hypothesis).
no_action.

Actions with side effects must be separated from pure reasoning.

12.3 Rule priority

Rules may include:

priority(Integer).

Higher values run first.

Priority must affect scheduling only, not logical truth.

12.4 Rule conflicts

When two applicable rules produce incompatible conclusions, the system must:

1. preserve both derivations;
2. compare statuses and scopes;
3. check whether their assumptions differ;
4. report a conflict;
5. avoid silently selecting one unless a declared conflict-resolution rule applies.

14. Reasoning engine

The reasoner must support:

* forward chaining;
* limited goal-directed backward chaining;
* cycle detection;
* duplicate-conclusion detection;
* assumption tracking;
* provenance;
* failure explanations;
* bounded search.

14.1 Forward reasoning

Starting from known facts, repeatedly apply eligible rules until:

* the requested conclusion is reached;
* no more rules apply;
* a configured step limit is reached;
* a cycle is detected;
* a contradiction is reached.

14.2 Backward reasoning

For a target conclusion:

1. find rules capable of producing it;
2. inspect their conditions;
3. recursively seek the conditions;
4. use memoisation to avoid repeated subgoals;
5. stop at configured depth;
6. report missing conditions.

14.3 Reasoning limits

Required options:

set(max_reasoning_steps, Integer).
set(max_reasoning_depth, Integer).
set(max_generated_hypotheses, Integer).
set(max_choice_product, Integer).

The system must stop safely when limits are reached and explain which limit was reached.

14.4 Truth handling

The first release must support at least:

truth(true).
truth(false).
truth(unknown).
truth(conflict).

Do not use negation as failure as equivalent to logical falsity in stored MNN knowledge.

Required trace event forms:

trace_event(

15.1 Summary trace

A summary trace must show:

* question;
* principal facts;
* rules applied;
* conclusion;
* status;

15.2 Full trace

A full trace must show every relevant intermediate event.

15.3 Trace export

Support export to:

* Prolog terms;
* plain text;
* JSON when feasible;
* Graphviz DOT for dependency and reasoning graphs.

16. Dependency engine

Required forms:

mnn_dependency(
    From,
    To,
    Type,
    Metadata
).

Supported dependency types:

positive.
negative_constraint.
data.
control.
ordering.
resource.
effect.
proof.
optional.

16.1 Positive dependencies

A positive dependency means the target requires the source.

mnn_dependency(
    modular_test_result,
    primality_decision,
    positive,
    []
).

16.2 Negative constraints

A negative constraint invalidates or blocks a route.

mnn_dependency(
    small_factor_found,
    probable_prime_route,
    negative_constraint,
    []
).

16.3 Necessary-variable analysis

For a supported predicate, determine which variables and subgoals contribute to requested outputs.

Required interface:

necessary_variables(
    PredicateIndicator,
    RequestedOutputs,
    NecessaryVariables,
    NecessaryGoals,
    Diagnostics
).

The analysis may be conservative.

It must not remove a goal unless the system can justify that:

* its outputs are unused;
* it has no permitted side effects;
* it cannot affect success or failure;
* it cannot affect exceptions;
* it cannot affect answer order where order matters.

16.4 Dependency graph

Required interface:

build_dependency_graph(
    Target,
    Graph,
    Diagnostics
).

Graph nodes must include:

* identifier;
* inputs;
* outputs;
* status;
* cost estimate;
* effect classification.

17. Algorithm synthesis

The first release must support small synthesis tasks.

Required input forms:

mnn_example(
    ExampleId,
    Input,
    Output,
    Metadata
).
mnn_operation(
    OperationId,
    PredicateIndicator,
    Cost,
    Metadata
).
mnn_constraint(
    ConstraintId,
    Constraint,
    Status,
    Metadata
).

17.1 Supported synthesis classes

Initially support:

* finite decision trees;
* direct lookup;
* arithmetic expressions from a restricted operation set;
* structural recursion over lists;
* list mapping;
* list filtering;
* list duplication;
* list accumulation;
* simple state transitions.

17.2 Candidate ranking

Rank candidate algorithms by:

1. passes all mandatory examples;
2. obeys constraints;
3. terminates on required test set;
4. uses permitted operations;
5. minimum unsupported assumptions;
6. smaller program size;
7. lower estimated runtime;
8. lower estimated memory;
9. greater determinism;
10. easier traceability.

17.3 Candidate status

Generated algorithms must be labelled:

candidate_algorithm.
verified_on_examples.
property_tested.
equivalence_verified.

Passing supplied examples must not be described as general proof.

17.4 Recursive synthesis

For list recursion, attempt templates such as:

predicate([], BaseOutput).
predicate([Head|Tail], Output) :-
    transform_head(Head, Partial),
    predicate(Tail, TailOutput),
    combine(Partial, TailOutput, Output).

Search must be bounded.

17.5 Decision-tree synthesis

Generate shared decisions rather than one clause per example when possible.

18. Optimiser

The optimiser must initially recognise selected patterns rather than arbitrary Prolog.

Required interface:

optimise_predicate(
    PredicateIndicator,
    Options,
    Original,
    Optimised,
    Trace,
    Diagnostics
).

18.1 Supported transformations

The first release should support:

* unused pure goal detection;
* common-prefix factoring;
* common-suffix factoring;
* repeated deterministic-call memoisation suggestions;
* repeated traversal detection;
* selected findall/3 analysis;
* simple loop fusion suggestions;
* subterm-index suggestions;
* deterministic branch conversion;
* explicit dependency extraction.

18.2 Transformation status

Each transformation must be classified as:

safe_static.
verified_by_tests.
candidate_only.
unsupported.

18.3 No unverified semantic claims

The optimiser must not claim semantic equivalence unless:

* equivalence was formally established for the supported pattern; or
* bounded or property-based comparison was completed and described accurately.

18.4 Fallback

Unsupported constructs must not crash the whole conversion.

The optimiser should preserve the original code and issue diagnostics.

⸻

19. Loop conversion

Implement a limited Loop2-style conversion layer.

19.1 Findall analysis

Recognise:

findall(Template, Goal, Results)

and classify whether it can be converted into a deterministic loop.

The first release may support only goals based on:

* list traversal;
* between/3;
* known finite domain generators;
* simple deterministic transformations;
* selected multiple-clause enumerations.

19.2 Generated loops

Generated loops must explicitly represent:

* source;
* accumulator;
* transition;
* termination;
* final output.

19.3 Multiple-template collection

Where several findall/3 calls traverse the same finite source, propose a fused traversal.

19.4 Collection order

Generated output order must match the original supported source order.

19.5 Failure behaviour

The converter must preserve whether:

* no source values produce [];
* transformation failure skips an item;
* exceptions propagate.

memo_call(

The implementation must use safe SWI-Prolog storage.

Memoisation options:

memo_mode(off).

memo_mode(domain).

Default:

memo_mode(session).

21. Choice packets

Implement Detlog-style explicit alternatives.

Canonical representation:

cp(Values)

Requirements:

* Values must be a finite proper list;
* order must be preserved;
* duplicate handling must be configurable;
* unbound values must be rejected by default;
* an empty choice packet must produce a diagnostic;
* nested choice packets must be supported or explicitly normalised.

21.1 Required predicates

choice_packet(Term).
normalise_cp(Input, Output).
cp_values(CP, Values).
cp_map(Predicate, CPIn, CPOut).
cp_filter(Predicate, CPIn, CPOut).
cp_first(CP, Value).
cp_select(Predicate, CP, Value).

⸻

22. Splicing

Required predicates:

splice(+ChoiceTerms, -Rows).
splice_collect(+ChoiceTerms, -Rows).
splice_each(+ChoiceTerms, :Consumer).
splice_first(+ChoiceTerms, -Row).
splice_select(+ChoiceTerms, :Predicate, -Row).

Required behaviour:

?- splice(
       [cp([1,2]), cp([3,4])],
       Rows
   ).
Rows = [
    [1,3],
    [1,4],
    [2,3],
    [2,4]
].

Requirements:

* accept mixtures of fixed values and cp/1;
* preserve left-to-right enumeration;
* support nested choice packets;
* estimate product size before materialisation;
* warn or stop when the configured maximum is exceeded;
* provide streaming enumeration through splice_each/2;
* avoid hidden unrestricted choicepoints in collection predicates.

The strict design rule is:

Splice early, constrain before expansion, and enumerate late.

⸻

23. Explicit deterministic control

Provide the following predicates:

if_commit(+Condition, :Then, :Else).
first(:Generator, -Result).
once_det(:Goal).
guard(+Condition).
decision(+Input, -Branch).
loop_exit(+Reason).

These predicates must have documented deterministic or semideterministic behaviour.

The first release does not need to convert every Prolog cut automatically.

It should classify cuts encountered during analysis as:

green_cut.
deterministic_clause_selection.
first_solution_cut.
state_transition_cut.
unsafe_cut.
unknown_cut.

Unsafe cuts must remain unconverted.

24. Scheduler

The scheduler must operate on explicit task descriptions.

Required task form:

mnn_task(
    TaskId,
    Goal,
    Inputs,
    Outputs,
    Dependencies,
    Metadata
).

Metadata may include:

cost_estimate(Number).
failure_estimate(Number).
purity(pure).
purity(effectful).
priority(Number).
deadline(Milliseconds).
resource(cpu).

24.1 Readiness

A task is ready when:

* all mandatory dependencies are satisfied;
* required inputs are available;
* no negative constraint has invalidated it;
* effect ordering permits execution.

24.2 Sequential scheduling

Sequential mode must produce a valid topological order.

24.3 Parallel scheduling

Use SWI-Prolog threads for pure tasks where enabled.

The scheduler must:

* use a bounded worker pool;
* avoid creating one thread per trivial goal;
* batch small tasks where useful;
* collect results safely;
* propagate exceptions;
* support cancellation;
* preserve declared ordering constraints.

24.4 Failure-aware scheduling

Cheap tasks likely to invalidate a branch may be prioritised.

Suggested scheduling score:

priority score =
    elimination estimate
    × relevance estimate
    ÷ cost estimate

This is a heuristic for scheduling only.

24.5 Stacked scheduling

The scheduler should not require a global barrier after every group.

When a task completes:

1. record outputs;
2. mark dependent tasks ready;
3. submit newly ready tasks;
4. cancel invalid tasks;
5. continue until target completion.

24.6 Speculative scheduling

Speculative mode may run only tasks classified as:

purity(pure).
reversible(true).

No speculative task may:

* write files;
* send network requests;
* alter persistent state;
* perform robot actions;
* call assertz/1 or retract/1 outside isolated internal storage;
* produce irreversible output.

research(

* explicit correlation search;

28. Correlation discovery

The program may search for patterns such as:

correlation(
    Conditions,
    Conclusion,
    Support,
    Status
).

Initial correlation methods:

* exact implication over supplied examples;
* exclusion;
* repeated co-occurrence;
* repeated ordering;
* deterministic mapping;
* necessary-condition candidate;
* sufficient-condition candidate.

A discovered correlation must initially be:

status(candidate).

It may become:

status(empirically_supported(Data)).

after testing.

It must not become proven without a logical proof.

⸻

29. Formula discovery

Support limited formula search using:

* constant formulas;
* linear formulas;
* simple polynomial formulas;
* finite differences;
* ratios where defined;
* recurrence candidates;
* Gaussian elimination for linear coefficient systems.

Required interface:

discover_formula(
    Examples,
    AllowedForms,
    Formula,
    Evidence
).

The output must include:

* matched examples;
* failed examples;
* assumptions;
* candidate status;
* complexity.

⸻

30. Invariant discovery

Required interface:

discover_invariant(
    ProcessExamples,
    CandidateInvariant,
    Evidence
).

Initial invariant forms may include:

* constant list length relation;
* conserved sum;
* conserved count;
* monotonic value;

47. Coding standards

The implementation must:

* use modules;
* avoid unnecessary global dynamic state;
* document exported predicates;
* include mode comments where useful;
* use meaningful variable names;
* avoid singleton-variable warnings;
* avoid silent exception swallowing;
* validate external input;
* keep pure reasoning separate from effects;
* preserve deterministic declarations where possible;
* use setup and cleanup around temporary resources;
* remain readable to an experienced Prolog programmer.

Prefer clear Prolog over excessively abstract metaprogramming.

48. Final design principle

The system must be built around the following rule:

Every conclusion, optimisation, schedule and research hypothesis must be represented in a form that can be inspected, tested and, where applicable, independently verified.

The first release succeeds when it provides a reliable transparent foundation. It does not need to solve unrestricted artificial intelligence, mathematical discovery or program optimisation.

The priority order is:

correctness
→ transparency
→ determinism
→ safety
→ testability
→ usefulness
→ performance
→ broader research capability
